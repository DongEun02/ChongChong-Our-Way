# 웹 접근성 개선

## 이유 확인 - 시작 전

> 이 요구사항이 왜 주어졌는지, 어떤 경험을 만들기 위한 것인지 파악합니다.
> **적용 전 상태(문제, 불편, 위험, 비효율, 학습 공백)를 먼저 남깁니다.**

웹 접근성은 스크린 리더를 사용하는 특정 행동에 제약이 있는 사용자도 마우스 클릭 없이 웹사이트를 사용할 수 있게 만드는 것이다.

현재 MVP는 화면을 직접 보고 마우스 또는 키보드를 사용하는 사용자를 중심으로 구현되어 있다. 키보드만 사용하거나, 스크린리더를 사용하는 경우 동일한 기능을 이용할 수 없다. 따라서 스크린 리더 사용자를 위해 접근성을 적용하는 것이 이번 요구사항이다.

현재까지 접근성을 적용하라고 하면 단순히 id, name, aria 속성만 사용해 label과 input 등을 연결시키만 했을 뿐 시맨틱 HTML, 접근성 트리, 스크린 리더가 실제로 어떻게 연결되고 동작하는지 잘 모르는 상태이다.

## 적용 - 실제 서비스에

> 기술을 학습하고, 실제 팀 프로젝트 서비스에 적용합니다.

### 다이얼로그

#### Before

Screen Recording 2026-08-30 at 1.57.49 PM.mov

스크린리더에서 스터디 삭제와 같이 조금은 강력한 기능을 가진 버튼을 클릭했을때 `ConfirmDialog`가 열리게 된다.

현재 다이얼로그가 열렸을때 바로 취소버튼으로 향하게 된다.

왜냐하면 showModal호출시 다음과 같이 포커스할 요소를 찾기 때문이다.

1. autofocus가 명시된 속성 찾기
2. 하위 트리 순서상 첫 번째 포커스 가능 요소
3. 없다면 dialog 자체

해당 다이얼로그가 열렸을때 **“스터디를 삭제할까요?”** 라는 문구가 스크린리더에서 가장 먼저 읽힌다.

문제는 현재 헤딩부분만 읽어준다는것이다.

사실 이 다이얼로그의 핵심적인 주의사항은 description 부분에 명시되어있다.

**“삭제한 스터디는 다시 복구할 수 없어요. 정말 삭제하시겠어요?”**

스크린리더 사용자들 또한 이 문구가 자동으로 읽혀야한다.

물론 요소를 위로 이동하여 확인할 수 있지만 우리와 같이 시각적으로 해당 요소를 판별할 수 있기에 가능한 판단이다.

스크린 리더 사용자는 경고메시지인 description을 인지하지 못한채 스터디를 삭제할 가능성이 존재한다.

**물론 다이얼로그 첫 요소부터 탐색하게 하면 된다**

하지만 다이얼로그내에 많은 요소가 존재하게 된다면 스크린리더 사용자 입장에서 그 만큼 많은 요소를 지나쳐가야 한다는 비용이 생긴다.

이 비용은 생각보다 크고 오히려 목적대비 불필요한 데이터까지 들어야 하는 상황이 발생한다.

(그렇기에 하나의 목적의 다이얼로그에 알맞는 autofocus 설정도 필요하다)

</aside>

#### After

이번에는 Dialog에 `role=”alertDialog”`와 `aria-labelledby`, `aria-describedby` 를 사용하여 헤딩과 디스크립션을 연결시켰다.

Screen Recording 2026-08-30 at 2.05.54 PM.mov

이번에 다시 스크린리더를 사용하여 접근해보니 똑같이 취소버튼에 가장 먼저 포커스되지만 이전과 달리 **“삭제한 스터디는 다시 복구할 수 없어요”** 라는 설명이 포함된다.

이 과정은 aria-labelledby와 aria-describedby로 헤딩과 디스크립션을 연결시켜주었고 alertDialog role을 주어 포커스가 취소 버튼에 가더라도

스크린리더가 대화상자에 진입하는 시점에 제목과 설명을 함께 읽어주도록 했다.

## 관찰 - 적용 후

> 적용 후 무엇이 달라졌는지 확인합니다.
> 데이터, 로그, 화면, 대시보드, 팀 피드백, 사용자 반응 등 확인한 것을 남깁니다.

우리는 언제나 시각적으로 무언가에 의미를 담아서 표현했을때 의심해야한다.

우리에게 잘 보이고 구분되는 색상일지라도 남들또한 잘 보이는지에 대해서도 의심해야한다.

우리가 쉽게 클릭할 수 있는 요소라고 느낄때 손떨림이 많은 사용자또한 쉽게 클릭(인터렉션)할 수 있는지 의심해야한다.

우리는 쉽게 요소들을 탐색할 수 있지만 스크린리더 사용자또한 해당 요소를 탐색하기 위해서 어떤 과정을 밟아야 하는지 의심해야한다.

우리는 하나의 요소가 어떤 것들을 담아내고 있는지 알고있지만 스크린리더 사용자또한 그 의미를 전부 파악할 수 있는지 의심해야한다.

결국 웹 접근성은 색각 이상자 시각 장애인 또는 손떨림이나 저시력자(터널 시야)를 가진 사람들

즉, 웹을 사용하는데 불편함을 가진 사람들이 정상적인 사람들과 거의 유사할 수 있는 웹 경험을 제공할 수 있도록 목표해야한다.

**“우리와 유사한 경험을 할 수 있나요?, 우리와 동일하게 이 요소를 이해할 수 있나요?”**

웹의 특정 요소를 만들어나갈때 매번 자신에게 해야할 중요한 질문이지 않을까 싶다.

## 기록과 설명

> 수행 내용과 판단 근거를 문서로 남깁니다.

현재 프로젝트에서 접근성 문제가 존재하는 부분들을 개선해 보았습니다.

시각적 특징으로 표현한 데이터(프로그래스 바(width색상), 하단 탭바에서 액티브 탭(색상)) 를 위주로 접근성 문제를 파악했습니다.

특정 부분들이 스크린리더 사용자도 이해할 수 있을지 고민해보고 실제 스크린리더로 접근해보면서 어떤 문제점이 있는지 확인했습니다.

과제 제출 현황의 프로그래스 바는 화면상으로 2/4와 50%가 올바르게 표시되고 있었지만, 접근성 속성인 `aria-valuemax`와 `aria-valuenow`가 반대로 설정되어 있었습니다. 그 결과 스크린리더에서는 진행률을 100%로 잘못 안내했습니다.

전체 멤버 수를 최댓값으로, 제출 완료 인원수를 현재 값으로 전달하도록 수정해 시각적으로 표현되는 정보와 스크린리더가 읽는 정보를 일치시켰습니다.

하단 탭바는 현재 탭을 초록색 아이콘과 글자로 구분하고 있었지만, 스크린리더에서는 모든 탭을 동일한 링크로 안내해 현재 위치를 알기 어려웠습니다.

하단 탭바는 페이지를 전환하는 내비게이션이므로, 활성 링크에 `aria-current="page"`를 적용해 현재 페이지임을 함께 안내하도록 개선했습니다.
