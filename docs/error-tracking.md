# 에러 트래킹 환경 구축

## 이유 확인 - 시작 전

> 이 요구사항이 왜 주어졌는지, 어떤 경험을 만들기 위한 것인지 파악합니다.
> **적용 전 상태(문제, 불편, 위험, 비효율, 학습 공백)를 먼저 남깁니다.**

전문 QA 팀이 없는 환경에서는 서비스에서 발생하는 오류를 미리 발견하기 어렵다. 단순한 네트워크 오류나 API 응답 오류는 개발 과정에서 비교적 쉽게 확인할 수 있지만, 특정 브라우저나 운영체제, 기기 상태, 사용자의 행동 순서와 같은 외부 요인이 결합해 발생하는 오류와 런타임 오류는 예측하기 어렵다. 개발 환경에서 정상적으로 동작하더라도 실제 사용 환경에서는 언제든 예상하지 못한 문제가 발생할 수 있다.

오류가 발생한 사실을 알게 되더라도 당시의 실행 환경과 사용자 행동을 확인할 수 없다면 원인을 파악하기 어렵다. 사용자의 제보만으로 문제를 재현해야 하는 경우에는 오류가 발생한 화면, 입력값, 요청과 응답, 실행 환경 등의 정보가 충분하지 않을 수 있다. 재현에 실패하면 원인을 추측하며 코드를 살펴봐야 하고, 그만큼 문제를 해결하는 데 더 많은 시간이 든다.

사용자 제보에만 의존하는 방식에도 한계가 있다. 사용자가 불편을 겪고도 문제를 알리지 않으면 팀은 오류가 발생했다는 사실조차 알 수 없다. 제보가 접수되더라도 이미 여러 사용자가 같은 문제를 겪은 뒤일 수 있어 대응 시점이 늦어진다. 오류를 빠르게 발견하고 원인을 분석하려면 운영 환경에서 발생한 오류와 당시의 맥락을 자동으로 수집하고, 이를 팀이 지속해서 확인할 수 있는 환경이 필요하다.

## 적용 - 실제 서비스에

> 기술을 학습하고, 실제 팀 프로젝트 서비스에 적용합니다.

### Sentry 와 Posthog

에러 트래킹 도구로는 Sentry, Posthog 외에도 Datadog와 같은 수 많은 도구들이 존재한다.
하지만 우리는 오직 Sentry와 Posthog 둘 간의 차이를 비교하고 결정하기로 했다.
후보군을 둘로만 둔 이유는 지금 현재 모니터링에 이미 사용하고 있는 Posthog를 재사용할 수 있다는 점, 그리고 Sentry는 대표적인 에러 트래킹 도구라는 점에서 비교해 볼 가치가 있다고 생각했다.
이렇게 재사용과 대표 도구 둘간의 차이를 비교해보는게 지금 당장은 좋겠다고 판단했다.
수 많은 도구들을 두고 장단점을 파악하기에는 아직은 에러 트래킹에 대한 이해도 부족했고 이 두 도구만으로도 우리의 니즈를 달성하는데는 문제없다고 판단했다.

우리가 에러 트래킹 도구를 도입하려는 목적은 명확하다.
“실제 사용자가 어떤 에러를 마주했는가?”를 파악하고, 그 문제를 인지하고 재현하며 해결하기 쉬운 환경을 갖추는 것이었다.
이를 위해 다음과 같은 정보를 확인할 수 있어야 했다.

- 어떤 에러가 언제, 어떤 환경에서 발생했는가?
- 사용자는 에러가 발생하기 전에 어떤 행동을 했는가?
- 원인을 파악하고 재현하는 데 필요한 정보를 얻을 수 있는가?
- 얼마나 많은 사용자에게 영향을 주며, 어떤 문제부터 해결해야 하는가?

만약 발생 횟수가 많더라도 치명적인 영향을 주지 않는 버그가 있거나 발생 횟수가 적은데 정말 치명적인 버그가 있다고 가정했을때
우리는 위와 같은 기능들을 통해 우선순위를 유연하게 판단하고 의사결정을 내릴 수 있다.
결국, 에러 트래킹 도구를 두게 된다면 단순히 에러와 마주하는것을 넘어 더 세세한 판단을 해낼 수 있다.

이 두 도구의 차이점을 확인할 수 있는건 Posthog의 한 아티클을 통해 알 수 있었다. (근데 posthog 측에서 작성한거라 살짝 편향적일 수 있다)

[sentry vs posthog](https://posthog.com/blog/posthog-vs-sentry)

간단하게 정리해보면 먼저 posthog는 사용자 행동을 분석하고 제품을 개선하는 데 중심을 둔 플랫폼이다.
이벤트 분석, 퍼널, 리텐션, 세션 리플레이 등의 기능을 제공하며, 에러 트래킹도 이러한 사용자 데이터와 연결해서 활용할 수 있다.
그리고 우리는 이미 사용자 행동을 posthog로 관찰하고 있기 때문에 더욱 더 좋은 시너지를 낼 수 있겠다는 생각이 들었다.
즉, 에러가 발생했을때 사용자가 어떠한 흐름으로 행동하는지 사용자의 관점에서 더 세세하게 볼 수 있다.

Sentry는 애플리케이션의 오류를 발견하고 원인을 진단하며 해결하는 데 중심을 둔 도구다.
스택 트레이스로 오류가 발생한 코드와 호출 흐름을 확인하고, 오류 직전의 이벤트 기록인 브레드크럼을 통해 발생 맥락을 살펴볼 수 있다.
또한 오류의 발생 빈도와 영향을 받은 사용자 수를 확인하고, 담당자를 지정하거나 알림을 설정하는 등 문제 해결을 위한 기능을 제공한다.

Sentry는 그러면 사용자 관점에서 확인해볼 수 없는건가 ?

그건 아니다.
Sentry 역시 세션 리플레이를 제공하며, 오류와 연결된 사용자의 행동, 콘솔 출력, 네트워크 요청 등을 함께 확인할 수 있다.
우리가 중요하게 생각한 "사용자가 어떤 상황에서 에러를 마주했는가"는 두 도구 모두에서 살펴볼 수 있는 영역이었다.

하지만 Sentry는 뭔가 조금 더 에러 트래킹이라는 목적에 더 집중한 도구라는 점은 느껴졌다.
그 이유는 단순히 에러 파악을 넘어 지점, 빈도 까지 파악할 수 있기 떄문에 판단에 더 도움이 될거 같다.

### 도구 선택

우리팀은 이미 서비스 모니터링에 PostHog를 사용하고 있었기 때문에 PostHog의 에러 트래킹 기능을 활용하면 새로운 도구를 추가하지 않아도 된다는 장점이 있었다. 하나의 도구에서 사용자 행동과 오류를 함께 확인할 수 있어 운영할 도구의 수와 초기 설정 비용도 줄일 수 있었다.
또한 여러 플랫폼을 오갈 필요없이 하나 안에서 해결할 수 있다는점도 굉장히 유의미한거 같다.
우리와 같이 이러한 도구를 처음 도입하는 관점에서 이 부분은 더더욱 유의미하다.(어떤것이든 하나의 도구에 익숙해지는게 정말 중요하기 때문이다.)

하지만 우리는 그럼에도 불구하고 Sentry를 선택하게 되었다.
그 이유는 더 디테일한 에러 추적결과를 제공한다는 점이었다.
사실 우리가 사용자 흐름에서 에러를 관찰할 수 있는건 정말 좋은 점이다.
그렇지만 지금 상황에 특정 문제가 발생했을때 언제나 사용자의 흐름을 매번 봐가며 해결하기에는 시간적인 소요가 크다고 느껴졌다.
결국, 에러가 발생했을때 우리는 빠르게 의사결정 할 수 있는걸 더 중요하게 여겼다.
프로덕트가 초기단계이고 우리가 QA를 진행하지 못할때도 많다.(상황상)
그런 상황에서는 우리가 생각보다 많은 문제들을 마주하게 될것이다.
그리고 이 문제는 사용자가 마주하게 될것이고 우리는 그 문제점들 중에서 빠르게 우선순위를 판단하고 문제 지점을 파악하여 빠르게 해결해야 한다는걸 생각했다.
또 솔직히 말하면 Sentry가 에러 트레킹에 대표적이고 특화된 도구라는 점에서 사용해보고 싶은 마음도 조금 컸다.

### Sentry 초기화

진입점인 `frontend/main.tsx`에서 Sentry를 초기화했다. 초기화 코드는 애플리케이션 부트스트랩보다 먼저 실행되므로 렌더링 과정에서 발생하는 오류를 수집할 수 있다.

값이 있을 때만 Sentry를 활성화해 DSN이 설정되지 않은 로컬 환경이나 테스트 환경에서 불필요한 이벤트가 전송되지 않도록 했다. `SENTRY_ENVIRONMENT`에는 배포 환경을 나타내는 `DEPLOY_ENV`를 사용하고, 값이 없으면 Webpack의 빌드 모드를 사용한다. 같은 Sentry 프로젝트로 이벤트가 들어오더라도 `dev`와 `prod` 환경을 구분해 조회할 수 있다.

### 오류 수집

`createRoot`에 Sentry 오류 처리기를 연결했다. 처리되지 않은 오류뿐 아니라 Error Boundary에서 처리한 오류와 React가 복구한 오류도 같은 경로로 수집한다.

```tsx
ReactDOM.createRoot(rootElement, {
  onUncaughtError: Sentry.reactErrorHandler(),
  onCaughtError: Sentry.reactErrorHandler(),
  onRecoverableError: Sentry.reactErrorHandler(),
});
```

- `onUncaughtError`: React가 처리하지 못해 애플리케이션 밖으로 전파된 오류
- `onCaughtError`: Error Boundary가 처리한 오류
- `onRecoverableError`: React가 자동으로 복구했지만 확인이 필요한 오류

### 오류 발생 세션 재생

오류가 발생한 시점의 사용자 행동과 화면 흐름을 확인하기 위해 Session Replay를 활성화했다. 일반 세션의 수집 비율은 `0`, 오류가 발생한 세션의 수집 비율은 `1.0`으로 설정했다. 모든 사용자 세션을 저장하지 않고 오류 분석에 필요한 세션만 수집하려는 선택이다.

## 관찰 - 적용 후

> 적용 후 무엇이 달라졌는지 확인합니다.
> 데이터, 로그, 화면, 대시보드, 팀 피드백, 사용자 반응 등 확인한 것을 남깁니다.

현재까지는 배포 환경에서 에러가 발생하지 않아 이슈가 쌓이지 않았다.
또한 아직은 에러 트레킹에 대한 이해도가 부족한거 같다.
어떻게 이 도구를 고도화 해야할지 감이 잡히지 않는다.
이 부분에 대해서는 고민하고 있고 앞으로 개선해 나갈 예정이다.

## 기록과 설명

> 수행 내용과 판단 근거를 문서로 남깁니다.

### 현재 구현 범위

현재 구현은 브라우저에서 발생한 React 오류를 Sentry로 전달하고 오류 발생 세션을 재생하는 단계까지다. 사용자 행동 분석은 PostHog, 프런트엔드 오류 추적은 Sentry로 역할을 나눴다.

### 한계와 다음 단계

오류 이벤트 수집만으로는 Sentry를 선택한 목적을 모두 달성했다고 보기 어렵다. 릴리스, 커밋, 소스맵이 연결되어야 운영 번들의 오류 위치를 원본 코드에서 확인하고 문제가 발생한 변경 범위를 좁힐 수 있다. 다음 단계에서는 배포 파이프라인에 릴리스 생성과 소스맵 업로드를 추가하고, 의도적으로 발생시킨 오류로 전체 흐름을 검증한다.
