# 로딩 성능 개선

## 이유 확인 - 시작 전

> 이 요구사항이 왜 주어졌는지, 어떤 경험을 만들기 위한 것인지 파악합니다.
> **적용 전 상태(문제, 불편, 위험, 비효율, 학습 공백)를 먼저 남깁니다.**

총총은 PWA 앱으로 접속하는 사용자가 많아 모바일 환경에서의 로딩 성능이 중요하다.
사용자가 서비스에 진입한 뒤 콘텐츠를 보기까지 얼마나 기다리는지 확인하기 위해 Chrome DevTools의 Lighthouse를 모바일 조건으로 실행했다.

개선 전에는 FCP(First Contentful Paint)가 10.035초, LCP(Largest Contentful Paint)가 10.651초로 측정됐다.
첫 콘텐츠와 주요 콘텐츠가 표시되기까지 약 10초가 걸리는 상태였다.
반면 TBT(Total Blocking Time)와 CLS(Cumulative Layout Shift)는 낮게 나타나, 초기 리소스 로딩과 화면 표시 지연을 우선 개선 대상으로 정했다.

### 비교를 위한 측정 환경

총총은 local, development, production 환경의 설정이 서로 다르다.
서로 다른 환경에서 측정하면 코드 변경의 효과와 빌드 설정의 차이가 섞이므로, 개선 전후를 같은 조건에서 비교해야 했다.

운영 환경에서 비교하는 것이 가장 직접적이지만, 기능 배포와 별개로 성능 개선 실험을 반복해서 운영에 반영하기는 어려웠다.
따라서 개발 환경의 `webpack.dev.js`에서 `mode`를 `production`으로 변경해 배포하고, 운영과 유사한 빌드 조건에서 비교했다.
이는 성능 측정을 위한 설정이며, 운영 환경 자체에서 측정한 결과는 아니다.

| 항목        | 조건                                          |
| ----------- | --------------------------------------------- |
| 측정 대상   | 개발 환경에 배포한 production 모드 빌드       |
| 도구        | Chrome DevTools Lighthouse 13.5.0             |
| 기기        | 모바일                                        |
| 네트워크    | Slow 4G                                       |
| 제한 방식   | DevTools throttling, CPU 4배 감속             |
| 로그인 상태 | 카카오 로그인 유지                            |
| 집계 방식   | 개선 전후 각각 3회 측정 후 지표별 중앙값 비교 |

### 개선 후보

- **큰 JavaScript 번들:** `bundle.js`의 전송량은 약 1.29MiB였으며, 해당 측정에서 약 764KiB(58%)가 미사용 코드로 분류됐다. 첫 화면에서 필요하지 않은 코드를 나중에 불러올 여지가 있었다.
- **실제 표시 크기보다 큰 이미지:** 일부 SVG 안에 PNG가 Base64로 포함되어 있었다. 확장자가 SVG여도 파일 크기가 작지는 않았다.
- **렌더링을 차단하는 외부 폰트 CSS:** Pretendard CSS가 렌더링 차단 리소스로 확인됐고, Lighthouse의 예상 절감 시간은 약 1.26초였다. 이 값은 진단 도구의 추정치이며 실제 개선량과는 구분했다.

## 적용 - 실제 서비스에

> 기술을 학습하고, 실제 팀 프로젝트 서비스에 적용합니다.

### Lazy Loading으로 초기 번들 분리

처음부터 모든 컴포넌트를 불러오는 대신, 필요한 시점에 코드를 요청하도록 Lazy Loading을 적용했다.
로컬 production 빌드에서 메인 JS의 크기를 비교한 결과는 다음과 같다.

| 항목    | 변경 전    | 변경 후    | 감소량          |
| ------- | ---------- | ---------- | --------------- |
| 메인 JS | 1,354.5KiB | 1,240.8KiB | 113.7KiB · 8.4% |
| gzip    | 408.6KiB   | 371.0KiB   | 37.6KiB · 9.2%  |

추가로 `/studies` 경로에 바로 진입하는 사용자는 랜딩 페이지 코드를 즉시 사용할 필요가 없다고 판단했다.
랜딩 페이지도 라우트 단위로 분리해 해당 경로로 진입할 때 불러오도록 변경했다.

```tsx
{
  path: '/',
  lazy: async () => ({
    Component: (await import('./src/features/landing/App')).default,
  }),
}
```

랜딩 페이지까지 분리한 뒤 gzip 크기는 371.0KiB에서 271.2KiB로 추가로 26.9% 감소했다.

다만 Lazy Loading은 초기 번들을 줄이는 대신 페이지 진입 시 청크 다운로드 단계를 추가한다.
`/studies` 진입에서도 이 요청 단계가 생겼으므로 번들 크기만으로 로딩 성능을 판단해서는 안 됐다.

따라서 세션 복구와 페이지 청크 다운로드를 병렬로 진행하도록 개선했다.

### 표시 크기에 맞춘 이미지 최적화

`/studies` 헤더의 `header-icon.svg`는 화면에서 40×40px로 표시되지만, 내부에는 1324×1458px PNG가 포함되어 있었다.
파일 크기는 약 582KiB였다.
이 경우 SVG 코드만 정리하기보다 실제 표시 크기에 맞춰 해상도를 줄이고 WebP로 변환하는 편이 효과적이었다.

이미지를 매번 수동으로 변환하지 않도록 다음 도구를 빌드 과정에 연결했다.

| 도구                             | 역할                                     |
| -------------------------------- | ---------------------------------------- |
| `image-minimizer-webpack-plugin` | Webpack 빌드 과정에서 이미지 최적화 실행 |
| Sharp                            | 이미지 리사이즈·압축·WebP 변환           |
| SVGO                             | SVG의 불필요한 데이터와 코드 축소        |

일반 SVG import는 벡터 형식을 유지하면서 최적화하고, 크기 조정과 WebP 변환이 필요한 이미지는 import 쿼리로 지정하도록 구성했다.

```tsx
// SVG 형식을 유지하면서 최적화
import icon from './icon.svg';

// 너비 120px의 WebP로 변환
import logo from './header-icon.svg?width=120&as=webp';
```

원본을 직접 수정하지 않고 빌드 시 필요한 이미지를 생성하므로, 하나의 원본을 화면별로 다른 크기로 사용할 수 있다.
큰 배너 이미지에 적용한 결과는 다음과 같다. 아래 값은 네트워크 전송량이 아닌 파일 크기 기준이다.

| 파일                     | 변경 전  | 변경 후 | 감소율   |
| ------------------------ | -------- | ------- | -------- |
| `check-icon.svg` → WebP  | 1,869KiB | 15.3KiB | 약 99.2% |
| `laptop-icon.svg` → WebP | 460KiB   | 15.3KiB | 약 96.7% |

### 외부 폰트 CSS의 렌더링 차단 해소

기존에는 `index.html`에서 Pretendard CSS를 일반 스타일시트로 불러왔다.
이 외부 CSS가 초기 렌더링을 차단하는 리소스로 확인됐다.

```html
<link
  rel="stylesheet"
  href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css"
/>
```

폰트 파일 하나를 먼저 요청하고, 폰트 CSS는 preload로 불러온 뒤 로드가 완료되면 스타일시트로 적용하도록 변경했다.

```html
<link
  rel="preload"
  href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/packages/pretendard/dist/web/variable/woff2-dynamic-subset/PretendardVariable.subset.91.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
<link
  rel="preload"
  as="style"
  href="https://cdn.jsdelivr.net/gh/orioncactus/pretendard@v1.3.9/dist/web/variable/pretendardvariable-dynamic-subset.min.css"
  onload="this.onload = null; this.rel = 'stylesheet';"
/>
```

외부 폰트 CSS가 초기 렌더링을 막지 않게 하고, 폰트를 불러오는 동안 대체 폰트로 텍스트를 표시하도록 했다.

## 관찰 - 적용 후

> 적용 후 무엇이 달라졌는지 확인합니다.
> 데이터, 로그, 화면, 대시보드, 팀 피드백, 사용자 반응 등 확인한 것을 남깁니다.

개선 전과 같은 조건에서 Lighthouse를 3회 실행하고 지표별 중앙값을 비교했다.

| 지표        | 개선 전  | 개선 후 | 변화       |
| ----------- | -------- | ------- | ---------- |
| FCP         | 10.035초 | 7.520초 | 25.1% 단축 |
| LCP         | 10.651초 | 8.787초 | 17.5% 단축 |
| CLS         | 0        | 0       | 동일       |
| Speed Index | 10.818초 | 9.773초 | 9.7% 단축  |

첫 콘텐츠가 표시되는 시간은 약 2.5초, 주요 콘텐츠가 표시되는 시간은 약 1.9초 줄었다.
CLS는 0을 유지했다.

이 결과는 번들 분리, 이미지 최적화, 폰트 로딩 변경을 함께 적용한 뒤의 비교다.
각 변경이 FCP와 LCP를 얼마나 줄였는지는 이 측정만으로 분리해서 판단할 수 없다.

## 기록과 설명

> 수행 내용과 판단 근거를 문서로 남깁니다.

### 선택과 판단 근거

- **동일한 빌드 조건에서 비교** 개발 환경을 사용하되 production 모드로 빌드해 개발용 빌드 설정의 영향을 줄였다.
- **첫 화면에 필요하지 않은 코드를 분리** 미사용 코드 진단을 바탕으로 초기 번들을 줄였으며, `/studies` 직접 진입 시 불필요한 랜딩 페이지 코드도 분리했다. 측정 시 미사용으로 분류된 코드 전체가 서비스에서 불필요한 코드는 아니다.
- **이미지 내부와 표시 크기를 확인** SVG 확장자만으로 가벼운 자산이라고 판단하지 않고, 내부 PNG의 해상도와 실제 사용 크기를 비교해 변환 대상을 정했다.
- **폰트 로딩 중에도 콘텐츠 표시** 폰트 요청 시점을 앞당기면서 외부 CSS 때문에 초기 화면이 기다리는 시간을 줄였다.
