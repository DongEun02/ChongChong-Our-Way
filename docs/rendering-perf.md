# 렌더링 성능 개선

## 이유 확인 - 시작 전

공지 작성 폼에서 제목이나 내용을 입력할 때 다른 필드까지 함께 리렌더링되고 있었다. 입력 상태를 부모인 `NoticeForm`이 관리하기 때문에, 상태가 변경되면 하위 필드도 다시 렌더링되는 구조였다.

처음에는 모든 필드에 메모이제이션을 적용하는 방향을 생각했다. 하지만 리렌더링이 발생한다는 사실만으로 최적화가 필요하다고 판단하기는 어렵다. 어떤 필드에서 실제 비용이 발생하는지 먼저 React DevTools Profiler로 확인했다.

### 개선 전 측정

| 컴포넌트     | 렌더 횟수 |   평균 시간 |   누적 시간 |
| ------------ | --------: | ----------: | ----------: |
| 공지 폼 전체 |      43회 |     22.06ms |     948.4ms |
| 제목         |      43회 |      1.51ms |      65.0ms |
| 내용         |      43회 |      1.44ms |      62.1ms |
| **리마인드** |  **43회** | **17.23ms** | **741.1ms** |
| 첨부         |      43회 |      0.91ms |      39.0ms |

시간은 하위 컴포넌트를 포함한 렌더 시간이다. 부모와 자식의 시간을 더하면 중복 집계된다.

43개 커밋 모두 업데이트 시작점이 `NoticeForm`이었고, 매번 400개의 Fiber가 렌더링에 참여했다. 리마인드 필드는 전체 렌더 시간의 약 78%를 차지했다. 그 안의 `DatePicker`도 43번 렌더링됐으며, 누적 시간은 633.4ms였다.

코드에서는 날짜 선택기가 닫혀 있어도 `BottomSheet`가 자식을 마운트한 채 `visibility`로 숨기고 있었다. 따라서 폼이 렌더링될 때 화면에 보이지 않는 달력도 다시 렌더링될 수 있었다. 다만 프로파일링 파일만으로 당시 선택기가 열려 있었는지까지 확인할 수는 없다.

제목·내용·첨부의 평균 렌더 시간은 각각 1.51ms, 1.44ms, 0.91ms였다. 이 측정만으로 이 필드들까지 최적화해야 할 근거는 부족하다고 판단했다. 이번 작업은 비용이 크게 확인된 **공지 폼의 리마인드 필드 한 곳**으로 좁혔다.

## 적용 - 실제 서비스에

공지 폼에서 사용하는 리마인드 필드에만 `React.memo`를 적용했다.

```tsx
import { memo } from 'react';
import ReminderField from '../../../shared/widgets/ReminderField';

// NoticeForm 모듈 범위에서 한 번 선언한다.
const MemoizedReminderField = memo(ReminderField);
```

공지 폼에서는 기존 `ReminderField` 대신 다음 컴포넌트를 사용한다.

```tsx
<MemoizedReminderField
  id="notice-reminders"
  value={remindAts}
  onChange={setRemindAts}
  disabled={isSubmitting}
  helpText="설정한 시각마다 읽지 않은 스터디원에게 알림을 보내드릴게요"
  errorText={fieldErrors.remindAts}
/>
```

제목이나 내용만 수정할 때는 `remindAts`의 참조가 유지된다. `useState`의 setter인 `setRemindAts`도 참조가 안정적이다. 나머지 props 역시 값이 같으므로, `memo`의 기본 props 비교로 리마인드 필드의 렌더링을 건너뛸 수 있다. 이 경계에서 막으면 내부 날짜 선택기와 달력도 함께 건너뛴다.

리마인드를 등록하거나 삭제하면 `remindAts`가 바뀌므로 정상적으로 다시 렌더링된다. 제출 상태나 오류가 바뀌는 경우에도 `disabled`, `errorText` 변경이 반영된다. 이를 위해 별도의 `useCallback`이나 사용자 정의 비교 함수를 추가할 필요는 없었다.

공용 `ReminderField` 자체를 수정하지 않은 이유는 적용 범위를 제한하기 위해서다. 과제 생성에도 마감일·리마인드 필드가 있지만, 이번에 측정한 대상은 공지 폼이었다. 과제의 렌더링 비용은 확인하지 않았으므로 기존 구현을 유지했다. 제목·내용·첨부 필드와 공용 첨부 훅에도 최적화 변경을 남기지 않았다.

### 전후 비교

| 지표                       | 개선 전 | 개선 후 |

| 공지 폼 업데이트           |    43회 |    43회 |

| 내부 DatePicker 렌더링     |    43회 |     0회 |

공지 폼의 업데이트 횟수는 그대로였지만, 리마인드와 내부 달력의 추가 렌더링은 발생하지 않았다. 이번 두 기록에서 평균 렌더 시간은 약 **53.5% 감소**했다.

제목·내용·첨부는 여전히 43번 렌더링됐다. 다른 필드를 모두 메모이제이션하지 않고도, 비용이 큰 하위 트리 하나를 건너뛰는 것으로 전체 렌더 시간을 줄일 수 있었다.

## 기록과 설명

이번 작업에서 판단 기준으로 삼은 것은 리렌더링 횟수와 실제 비용이었다. 모든 필드가 같은 횟수로 렌더링돼도 비용은 같지 않았다. 측정 결과에서 대부분의 시간을 차지한 리마인드 필드만 개선 대상으로 정했고, 적용 후 그 하위 트리가 실제로 렌더링되지 않는지 다시 확인했다.

메모이제이션 범위도 공지 폼 안으로 제한했다. 공용 컴포넌트를 변경해 측정하지 않은 다른 화면까지 영향을 주는 대신, 확인한 문제를 해결하는 데 필요한 변경만 남겼다.
