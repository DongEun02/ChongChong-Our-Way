# 렌더링 전략 수립

## 이유 확인 - 시작 전

렌더링 전략은 중요하다.

전략이 중요한 이유는 프로젝트의 특징에 따라 요구하는 목표를 제공해야 하기 때문이다.(우리는 SEO가 중요해요.., 우리는 각 페이지를 공유했을때 각자마다 페이지에 알맞는 컨텐츠를 표시해야해요... 등등)

물론 목표또한 중요하지만 이 전략이 더더욱 중요한 이유는 비용이라고 생각한다.

렌더링 전략은 비용이 크다.

즉, 전환 비용이 크기 때문에 만약 우리가 CSR을 적용해왔다가 중간에 SSR을 적용해야 한다면 머리가 조금 아파질 수 있다.

프론트엔드 입장에서는 거의 기반을 바꾸는 것이기에 아주 큰 변경사항이며, 그렇기에 초기에 잘 설계하고 선택해야하는 부분중 하나이다.

만약 CSR을 적용해오던 프로젝트에서 SSR 체제로 전환하게되어 Next 프레임워크를 도입한다고 가정해보자.

그러면 우리가 서버에서 응답할 HTML을 만들때 호출할 API를 옮기고 만약 Suspense로 로딩상태를 보여줬다면 기존과 유지하기 위해서는 Streaming 방식을 채택하는등 수 많은 Next API로 전환함과 더불어 기존과 유지해야하는 부분들을 고민하는 비용이 상당할 것이다.

그렇기에 다양한 렌더링 전략을 파악하고 우리의 프로젝트에 알맞는 렌더링 전략을 선택하는게 정말 중요하다.

### 다양한 렌더링 전략과 장/단점

#### CSR

사용자가 웹에 접근하면 서버는 기본적인 HTML 뼈대와 JavaScript 파일을 제공한다.

브라우저는 HTML을 파싱하고, script 태그에 연결된 JavaScript 번들을 다운로드해 실행한다.

실행된 JavaScript가 화면에 필요한 요소를 생성하고, 필요한 경우 API를 통해 데이터를 받아 화면을 렌더링한다.

즉, **"화면을 구성하는 주요 작업이 브라우저에서 이루어지는 방식"** 이다.

> 장점이 뭔가요 ?

- 쉽다 ! 배포가 정말 쉽다. 빌드한 정적파일을 CDN으로 제공하기만 하면 된다. 그렇기에 SSR처럼 별도의 서버가 필요없다.

> 단점이 뭔가요 ?

- 렌더링 전에 JS를 요청한다. JS 메인번들은 기본적으로 무거운 파일이다. 그리고 이 JS 파일은 네트워크를 타게 됨으로써 시간적인면에서 소요가 있다. 그렇기 때문에 만약 네트워크 변수가 큰 상황일수록 더더욱 취약하게 된다.
  (코드스플리팅으로 어느정도 해소 가능 -> 현재 필요한 JS만 받는다. 그리고 필요할때 가져온다)

- 초기 콘텐츠 표시가 늦어진다. 이 이유는 첫번째 사유에 의함이 크다.

- 기존 HTML에서 컨텐츠를 갈아끼우는 형태이다. 그렇기에 페이지별 메타가 필요한 경우에는 제공하기 어렵다. 이 영향은 검색엔진이나 OG와 같은 구성(링크 미리보기)을 제공하지 못한다.

#### SSR

서버에서 HTML을 만들어 제공하는 방식이다.

만약 특정 API를 호출하여 그 API를 기반으로 최종적인 화면이 그려진다고 가정했을때 SSR에서는 API를 서버에서 호출하여 API응답을 통해 완성된 HTML을 응답한다.

> 장점이 뭔가요 ?

- 아무래도 CSR과 달리 네트워크 환경을 덜탄다. 왜냐하면 서버에서 JS코드를 소유하고 있기에 CSR처럼 번들을 다운로드 하고 실행할 필요없이 서버가 소유하고 있어 서버가 실행하고 응답하면 된다.(즉 어딘가를 거칠 필요가 없어진다.)

- 네트워크 변수가 큰 상황에서 유리하다. 보통 서버를 두게 되었을때 API서버와 가까운 곳에 두게 된다. 그렇기에 거리적으로 가까운 서버와의 요청/응답은 속도적인 측면에서 이점이 존재한다.

- 사용자 기기의 성능적인 영향을 덜 탄다. CSR처럼 브라우저에서 요청하게 되면 CPU 가 좋지 않거나 네트워크가 좋지 않으면 더더욱 취약해진다. 하지만 SSR은 사용자 기기의 성능이 아닌 서버에서 작업을 수행하기 떄문에 서버의 성능에 영향을 받게 된다. 그렇기에 서버의 성능으로 사용자의 다양한 환경속에서도 동일한 경험을 제공할 수 있다.

> 단점이 뭔가요 ?

- 비싸다. 만약 우리의 서비스가 굉장히 흥한 서비스라면 우리의 서버는 굉장히 많은 비용을 내게 될것이다.

- 유지보수하기 어렵다. 왜냐하면 서버를 유지보수해야하기 때문에 클라이언트 개발자로써 서버에 대한 이해도 필요하고 만약 사용자가 많아 부하가 많은 타이밍이 있다면 Scaleup과 관련된 설계도 해야할것이다. 또 가용성적인 측면도 고려해야할 것이다. 결국 서버를 유지보수해야하기 때문에 서버를 운영하게 되면서 하게 되는 고민을 겪어야 한다.

#### Hybrid

서버사이드 렌더링과 클라이언트 렌더링을 같이 사용하는 방식이다.

서버사이드의 장점과 클라이언트 사이드의 장점을 결합했다.

> 장점이 뭔가요 ?

- CSR의 장점과 SSR의 장점을 함께 사용할 수 있다.

> 단점이 뭔가요 ?

- hydration이 생기게되면서 생각해야할 부분들이 늘어난다. 결국 서버에서 전달하는 초기 HTML과 클라이언트에서 hydartion을 수행하기 전 상태의 HTML이 동일해야한다. 즉, 서버가 생성한 HTML과 클라이언트의 첫 렌더링 결과가 일치해야 하므로, 이를 맞추기 위한 고려가 필요해진다.

- hydration과정이 오래 걸린다고 가정하면 CSR적인 측면의 장점을 활용하지 못하는 상황이 온다. 이 상황은 결국 사용자가 웹 사이트가 정상적으로 보이기는 한데 상호작용은 못하는 상황을 초래한다.

#### SSG

빌드 시점에 HTML을 미리 만들어 두고, 사용자가 웹에 접근하면 만들어 둔 HTML을 제공하는 방식이다.

만약 API 데이터가 필요한 페이지라면 빌드 과정에서 API를 호출하고, 응답 데이터를 기반으로 HTML을 생성한다.

SSR이 요청 시점에 HTML을 생성한다면, SSG는 빌드 시점에 HTML을 미리 생성해 두고 그걸 제공하는 방식이다.

> 장점이 뭔가요 ?

- 빠르다! 왜냐하면 미리 만들어 둔걸 바로 제공하면 되기 떄문이다. 즉 정적인걸 제공하기 때문에 CDN을 활용할 수 있다.

- 초기 HTML에 콘텐츠와 페이지별 메타 정보를 포함할 수 있다. 이 장점은 SSR과 동일하다.

> 단점이 뭔가요?

- 빌드된 시점의 형태이기 때문에 만약 변경사항이 생긴다면 매번 빌드해야할것이다. 그렇기에 빌드 <-> 배포 작업이 잦아진다. (만약 그 작업이 오래걸린다면 ? 그리고 그 틈의 시간이 중요하다면 ?)

- 권한이나 인증과 같이 요청 시점이후에 결정되는 부분을 대응하기 어렵다. 왜냐하면 이러한 부분들은 빌드시점에는 알 수 없기 때문이다. 그렇기에 결국 SSG만을 사용하기에는 한계가 있다.

#### Native

기기에 설치된 앱이 플랫폼의 UI 기능을 사용해 화면을 구성하는 방식이다.

화면을 구성하는 코드와 리소스가 앱에 포함되어 있다.

그렇기에 웹처럼 서버에서 HTML이나 JS 번들을 받아야 화면을 그릴 수 있는 구조는 아니다.

물론 필요한 데이터는 API를 통해 별도로 가져온다.

> 장점이 뭔가요 ?

- UI 코드가 앱 바이너리에 포함되어 있기 때문에 빠르게 렌더링 할 수 있다. 그래서 만약 초기화면을 눌렀을때 바로 보여야한다면 Native일때 가능하다.(초기화면을 빠르게 보여줘야할때 유리)

- 기기 자체의 네이티브 기능이 필요할때 유용하다. 알림, 위치, 카메라와 같은 기능이 필요하다면 Native 상황에서는 사용하기 좋다.

- 플랫폼에 맞는 자연스러운 사용자 경험을 제공하기 좋다. 우리가 앱에서 사용하는 간단한 제스처와 같은 상호작용을 제공하기 때문이다.

> 단점이 뭔가요 ?

- 배포할때마다 스토어 심사해야한다. (RN을 쓴다면 해결가능, 근데 네이티브적 장점을 잃음)

- IOS, Android를 따로 개발해야하기 때문에 각각을 유지보수해야하는 비용이 생긴다. 심지어 언어도 둘 다 다르다. (RN이면 해결할 수 있지만 여전히 트레이드오프 있다)

## 적용 - 실제 서비스에

> 총총은 네트워크 변수, 기기 성능의 영향을 많이 받는가 ?

총총의 예상 사용자 타겟은 한국인들이며 나이대는 20 ~ 30대이다.

보통 우리나라 사람이며 나이대가 20 ~ 30대인 사람들은 좋은 핸드폰 기기를 사용한다. (50대 이상이 아닌 이상)

또한 우리나라 자체의 네트워크가 훌륭할 뿐더라 총총이 만약 지하철과 같이 네트워크 환경이 좋지 않은 곳에서 자주 사용될 가능성은 크지 않다.

물론 과제나 공지를 작성하거나 현황을 확인하는걸 지하철, 엘레베이터와 같이 네트워크가 좋지 않은 상황에서 수행할 수는 있겠지만 그럴 가능성은 낮다.

그렇기에 네트워크 변수를 특별히 고려해야할 필요성은 낮다고 판단했다.

그래도 우리가 고려한다면 차라리 네트워크가 좋지 않은 환경에서의 UX 개선이 더 나을거같다.

만약 공지나 과제의 경우는 장문으로 작성하게 되는 경우가 있을것이고 휘발되면 UX에 특히 좋지 않다.

이러한 상황을 대비하여 작성하고 있는 내용을 LocalStroage와 같이 사용자의 브라우저에 저장하는 식을 통해 휘발되더라도 복구하는 로직을 두어 UX를 개선할 수 있다.

> 총총의 LCP, FCP 중요한가 ?

중요하다. 사실 LCP, FCP가 안중요한 앱은 없다.

하지만 엄청나게 중요한건 아니다.

만약 실시간으로 데이터를 확인해야하는 앱인경우 중요할 것이다.

하지만 총총은 실시간으로 확인할 필요는 딱히 없다.

그래도 성능은 중요하다.

그렇기에 신경은 쓰지만 LCP, FCP와 같이 결국 로딩성능을 위해 렌더링 전략을 바꾸는건 정말 최최최최최후의 방법인데, 현재 운영 환경의 경우 LCP, FCP 모두 1초 이내로 측정된다.

따라서 이미 성능이 좋은데 억지로 전략을 바꾸는 것은 불필요한 비용만 증가시킨다.

코드 스플리팅을 하여 번들을 청크별로 두어 사이즈를 줄이거나 사용되는 이미지를 더 적절한 확장자를 사용하여 가져오는 비용을 줄이는등

렌더링 전략이 아닌 다른 성능 개선 방법들을 모두 시도하고 나서도 만약 특정 시간 이내로 진입하지 못한다.

그리고 꼭 그 시간 내로 진입해야한다.

이런 상황이라면 렌더링 전략을 바꿔야할것이다.

아무튼 중요하지만 렌더링 전략 선택에 영향이 가는 정도는 아니다.

> 총총 SEO 중요한가 ?

중요하지 않다.

총총은 웹에서 검색을 통한 사용자 유입을 고려하지 않았다.

총총은 스터디 관리앱으로써 우리가 생각하는 유입의 경로는 스터디리드가 총총앱을 알게되고 그 총총 앱의 초대코드를 통해 스터디원을 초대하는 구조다.

여기서 스터디리드가 총총앱을 알아가는 경로 또한 검색이 아닌 홍보나 지인과 같은 수단으로 사용자가 스스로 찾는게 아닌 누군가의 권유에 의해 사용하게 되는걸 생각했다.

또한 총총은 개별 페이지가 존재하지 않는다.

개별 스터디는 존재하지만 스터디가 Private한 형태이기에 오히려 검색에 의해서 당연히 보여지면 안된다.

그렇기에 우리가 생각하는 총총 유입경로를 생각하면 SEO가 중요하지 않고 검색엔진에 의해 노출되지 않아도 괜찮다고 판단했다.

> 총총 링크 미리보기 중요한가 ?

미리보기 지금 당장은 중요하지 않다.

왜냐하면 미리보기가 중요해지는 경우는 결국 개별 컨텐츠 자체가 공유시에 각 컨텐츠가 드러나야한다.

총총의 가장 상위의 개별 컨텐츠는 스터디이다.

그리고 스터디는 Private이고 당연히 스터디에 의존하는 하위 컨텐츠 또한 Private이다.

그렇기에 누군가 스터디를 공유할 이유 자체가 크지 않다.

즉, 스터디를 공유하는 형태가 아닌 초대링크를 공유하는 형태다.

물론 초대링크를 공유할때 어떤 스터디인지에 대한 정보가 들어가면 좋을것이다.

하지만 이거 하나를 위해 전략을 수정할 정도의 비용을 감당할건 아니다.

> 우리의 선택

서버사이드가 주는 장점인 SEO나 링크 미리보기, 성능과 같은 부분들보다는 간단하게 배포할 수 있으며 설정이 비교적 쉬운 CSR이 더 우리에게 적합하다고 판단했다.

사실 정확히는 CSR과 SSR보다는 CSR과 Native간에 고민을 많이했었다.

왜냐하면 총총의 핵심은 "알림"기능이라고 생각했고 결국 더 좋은 경험의 알림을 제공하기 위해서는 Native가 유리하기 때문이다.

하지만 Native를 도입했을떄 우리가 학습해야할 비용이 너무나도 컸다.

또한 당시에 우리 앱의 핵심이 "알림"이라고 생각하는건 아무런 검증없이 우리의 생각일 뿐이었기에 "알림" 하나만으로 네이티브를 선택하기에는 너무나도 큰 비용이었다.

그리고 우리는 결국 Native가 아닌 RN + WebView를 도입할것이기 때문에(앱안에서 웹을 띄우는 형태) 렌더링 전략은 사실상 동일하다.

그렇게 우리는 CSR로 시작했다.

## 우리는 앞으로도 CSR을 유지할것인가 ?

우리는 여전히 CSR방식을 사용하고 있다.

CSR방식의 단점또한 근본적인 로딩성능 개선인 코드스플리팅이나 이미지 최적화를 통해 최대한 줄여가고 있다.

아직 우리는 다른 방식을 선택해야하는 근거를 찾지 못했다.

하지만 다음과 같은 상황이 발생한다면 우리는 전략을 수정해야할 수도 있다.

> 총총 스터디가 공개형태가 되었다.

총총 스터디가 공개형태가 된경우에는 SEO적인 측면보다 공유적인 측면에서 미리보기의 중요성이 올라간다.

이제는 사람들이 총총을 공유할때 초대링크를 사용하는게 아닌 특정 스터디의 링크를 공유할것이기 때문이다.

여기서 스터디 링크를 공유했을때 해당 스터디가 어떤 스터디인지에 대한 컨텐츠가 담기지 않는다면 이건 공유하는 입장에서 좋지 않다.

결국 공유자가 따로 부가적인 설명이 따라와야할 것이다.

아니면 직접 클릭해서 확인해야할 것이다.

이런 상황에서는 스터디 디테일에 적절한 메타태그를 주어 공유시에 해당 스터디에 대한 정보가 담기게 해야한다.

**그렇다면 우리는 렌더링 전략을 수정하여 이 문제를 해결해야할까 ?**

그러면 우린 SSR이나 SSG와 같은 형태로 전환해야할까? CSR을 포기해야할까?

그건 아니라고 생각한다.

솔직히 말해서 이 개별 메타, OG만을 위해 전환하기에는 비용이 너무나도 크다.

그렇기에 CSR을 유지하면서 개별 메타를 제공할 수 있는 방법을 찾아야한다.

결국 간단하게 말하면 이거를 위해 우리만의 서버가 필요해지는 상황은 최대한 막아야한다.

하지만 개별 메타는 제공해야하기 떄문에 다양한 선택지중에 트레이드오프를 고려하여 선택해야한다.

간단하게 가능한 몇가지 사항들을 이야기하면 다음과 같다.

1. 공유 URL에 스터디 이름과 이미지 정보를 담고 CloudFront Functions에서 OG 태그를 생성한다.
   구현은 단순하지만 URL이 길어지고, 정보가 바뀌어도 기존 링크에는 반영되지 않는다.

2. Lambda@Edge에서 공유 수집기의 요청을 구분하고 API로 스터디 정보를 조회해 OG 태그를 제공한다.
   기존 CSR과 간결한 URL을 유지할 수 있지만 함수 실행 비용과 API 지연, 수집기 판별 로직을 관리해야 한다.

3. 기존 백엔드에서 스터디별 OG 태그가 포함된 HTML을 제공하고 화면은 CSR로 구성할 수 있다.
   별도의 SSR 서버는 필요 없지만 프론트엔드 배포 결과와 HTML 응답을 연결해야 한다.

결국 필요한 것은 최초 HTML에 스터디 정보가 포함되는 것이므로, 전체 렌더링 전략을 바꾸기 전에 각 방식의 운영 비용과 복잡도를 비교하고 선택해야 한다.
