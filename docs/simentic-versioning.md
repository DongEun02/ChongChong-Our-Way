# 시맨틱 버저닝 적용

## 이유 확인 - 시작 전

### 현재 상태

현재 우리 총총팀은 배포를 다음과 같이 진행중에 있다.

기존 호환성을 깨트리는 변경을 의도적으로 발생 → 메이저 버전 업

새로운 기능 추가 → 마이너 버전 업

핫픽스, 버그 수정 → 패치 버전 업

버그로 인하여 빨리 배포를 해야하는 상황이 아니라면 특정 배포 시기를 정하여 그때 다음 버전을 릴리스 하는 편이다.

새로운 기능이 포함되면 마이너 버전 업을 하고 버그 수정만 존재하는 경우에는 패치 버전 업을 한다.

특별하게 기간으로 정한 릴리스 주기는 딱히 없고 목표로 정한다.

### 겪었던 문제점, 불편한점

시멘틱 버저닝과 관련하여 우리가 겪었던 문제점과 불편한점은 다음과 같다.

- 팀원에게 사전에 계획하지 않고 우리가 한 작업(UX개선)을 직접 말해야한다.

→ 각 버전마다 어떠한 변경사항이 존재하는지 기록하지 않고 있다. 릴리스 PR에 AI를 통해 요약하여 적지만 … 이게 적절한 방법인지는 모르겠다. 왜냐하면 지정한 프롬프트도 없고 매번 릴리스 하는 사람의 기준으로 작성된다. 또한 AI가 참조할 수 있는 데이터가 있을거고 그 데이터에 대한 우리의 규칙또한 없다. 그래서 만약 커밋으로 추론한다고 했을때 우리가 커밋을 잘못 작성하면 잘못 작성된 커밋이 릴리스 노트에 포함될 것이다.

- 치명적인 버그가 생겨서 롤백을 해야하는 경우, 롤백할 버전을 찾기가 어렵다.

→ 솔직히 말하면 아직은 롤백을 해야할 상황이 단 한 번도 오지는 않았다. 하지만 언젠가는 마주할 수 있는 상황이다. 이 상황과 마주했을때 우리는 빠르게 대응하기 어려울거 같다. 왜냐하면 우리가 명확하게 릴리스 노트를 기록하고 있지 않기 때문이다. 또한 특정 버전 커밋을 찾기가 어렵다. 태그를 붙이고 있지 않은 상태이며 아마 찾으려면 grep을 통해 특정 버전을 검색하는식으로 커밋 해시를 찾아야할것이다.

- 현재 버전을 알기 어렵다.

→ 태그나 Release 기능을 사용하고 있지 않아서 지금 현재 버전을 알기 어렵다. `package.json`에도 명시하고 있지 않으며 현재 어떤 버전인지 확인하려면 prod브랜치의 최신 커밋을 확인해야한다. 만약 다음 버전을 릴리스하려고 할때마다 이 부분에 대한 불편함이 생긴다.

이 세가지 문제점을 해결하면 될거 같다 !!

## 적용 - 실제 서비스에

`CHANGELOG.md` 를 추가했다.

해당 문서에는 각 버전별 변경사항(프론트엔드)이 담기게 된다.

```md
# Changelog

## 작성 규칙

- 사용자가 체감하는 변경을 한 줄로 작성합니다.
- 기능 추가는 Added, 버그 수정은 Fixed에 기록합니다.
- 변경 사항은 해당 PR에서 Unreleased에 추가합니다.
- 릴리스 준비 시 Unreleased의 내용을 버전과 날짜가 있는 항목으로 확정하고, 맨 위에 새로운 Unreleased를 만듭니다.
  - 예시: [1.0.0] - 2030-01-01
- 최신 버전이 위에 오도록 작성합니다.

## [Unreleased]

### 추가된 기능

### 개선 및 수정

### 종료된 기능
```

위와 같이 초안을 작성했다.

현재 프론트엔드 버전이 `1.0.0`이고, 다음 배포에 호환성을 유지하는 버그 수정만 포함되었다. 이제 `1.0.1`로 릴리스한다.(가정)

1. CHANGELOG의 `[Unreleased]` 내용을 `[1.0.1] - YYYY-MM-DD` 항목으로 확정한다.
2. 문서 상단에 새로운 `[Unreleased]` 섹션을 추가한다.
3. `package.json`의 버전을 `1.0.1`로 변경하고, 위 변경 사항을 포함한 PR을 작성해 `dev`에 병합한다.
4. `dev → prod` PR을 병합하고 배포한다. 배포 성공과 주요 기능의 정상 동작을 다시 한 번 확인한다.
5. 실제로 배포된 커밋에 `frontend-v1.0.1` 태그를 생성한다.
6. GitHub Release에서 해당 태그를 선택하고, CHANGELOG의 `1.0.1` 변경 내용을 복사해 게시한다. 운영 배포 시각과 커밋 해시도 함께 기록한다.

예상 Release 노트 형식

```md
# Frontend v1.0.1

## 개선 및 수정

- 날짜 선택기의 분 단위 선택 오류 수정
- 공지 제목이 잘리는 문제 수정

## 배포 정보

- 태그: frontend-v1.0.1
- 커밋: abc1234
- 배포 시각: YYYY-MM-DD, 시간
```

## 관찰 - 적용 후

현재 실제 새로운 버전에 적용해보지 않았다.

아직 새로운 버전이 나오지 않았기 때문이다.

그렇기 때문에 이미 존재하는 버전에 릴리스노트와 태그를 추가/작성해 보았다.

```md
# Frontend v2.0.5

## 추가된 기능

- 과제 제출물의 공개 범위를 설정하고, 공개된 스터디원 제출물을 확인하는 기능 추가
- 스터디 관리 화면과 스터디 이름/설명 수정 기능 추가
- 스터디의 현재 인원과 최대 인원 표시 추가
- 마이페이지에서 프로필 이름을 수정하는 기능 추가

## 개선 및 수정

- 스터디 삭제/탈퇴 버튼을 스터디 관리 화면으로 이동
- 지각 제출한 과제도 제출 완료 내역을 확인할 수 있도록 개선
- 스터디 수정 시 API 응답 처리 오류 수정
- 하단 탭의 클릭 영역 사이 공백 제거
- 알림 아이콘 화질 개선 및 마이페이지 이동 아이콘 적용

## 배포 정보

- 태그: frontend-v2.0.5
- 배포 커밋: 103c0ce6f2b273b3ec8331e1edc24c0433dc74d6
- 배포 시각: 2026-10-07, 10:47:05
```

이제 기존에 겪었던 문제점들을 기준으로 어떻게 바뀌었는지 확인해 보았다.

- 팀원에게 사전에 계획하지 않고 우리가 한 작업(UX개선)을 직접 말해야한다.

→ 이제는 작성된 Release Note를 통해 변경사항을 직접 확인할 수 있다.

- 치명적인 버그가 생겨서 롤백을 해야하는 경우, 롤백할 버전을 찾기가 어렵다.

→ 정상 배포했던 커밋에 버전 태그를 연결해 복구 후보를 식별할 기준을 준비했다. (실제 롤백은 아직 수행하지 않았지만 이제는 어디로 롤백해야할지 준비되어있다)

- 현재 버전을 알기 어렵다 (배포한 버전을 확인하기 어려웠다)

→ Release에 버전, 배포 커밋, 배포 시각을 기록해 배포 이력을 확인할 수 있게 했다

## 기록과 설명

도입 초기의 관리 부담을 줄이기 위해 버전 결정과 Release 게시는 수동으로 진행하기로 했다.

변경 기록은 CHANGELOG를 베이스로 삼아 PR에서 검토하고 릴리스 시 해당 내용을 GitHub Release에 게시한다.

프론트엔드 버전을 독립적으로 관리하지만 태그는 실제 배포한 커밋에 연결한다.

자동화와 관련해서는 불편함을 느꼈을때 고민해봐도 좋을거 같아 이번에는 제외했다.
