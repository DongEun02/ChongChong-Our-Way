# 테스트 전략 수립 및 지금까지 구현한 주요 기능에 대한 자동화된 테스트 작성

## 이유 확인 - 시작 전

> 이 요구사항이 우리 서비스의 어떤 문제와 연결되는지 정의합니다.
> **적용 전 상태(문제, 불편, 위험, 비효율, 학습 공백)를 먼저 남깁니다.**

테스트 환경이 없으면 기능 추가 이후 정상적으로 동작하는지 자동으로 확인할 수 없고 의도한대로 기능이 동작하는지, 혹시 다른 기능에서 오류가 발생한 건 아닌지 직접 확인해야 한다.

실제로 이전 프로젝트에서 컴포넌트 테스트나 E2E 테스트 코드를 작성하지 않아 기능을 추가하거나 리팩토링 후, 개발 서버를 열어 직접 조작하며 정상 동작하는지 확인해본 경험이 있다.

특히 공통 컴포넌트를 수정할 때 테스트 코드의 필요성은 더 중요해진다. ‘공통’인 만큼 해당 컴포넌트를 사용하는 곳은 다양하다. 하지만 이를 개발자가 모두 직접 확인하는 것은 효율적이지 않고 ‘모든 곳’을 확인해야 하기에 실수를 유발할 수 있다.

테스트는 우리가 지켜야할 최소한의 경계를 의미하며 우리가 코드를 수정했을때 그 경계를 깨트리지 않았는지 확인할 수 있게 해준다.

이로써 리팩토링과 같은 작업에서 안정성적인 측면에 아주 좋은 자신감을 채워준다.

## 적용 - 실제 서비스에

> 기술을 학습하고, 실제 팀 프로젝트 서비스에 적용합니다.

프로젝트의 테스트 범위를 단위 테스트, 컴포넌트 테스트, E2E 테스트로 구분하고 각각 Jest, React Testing Library, Playwright를 적용한다.

테스트 전략은 다음과 같다.

- Jest를 활용해 유틸 함수와 비즈니스 로직 등 독립적으로 검증할 수 있는 코드의 단위 테스트를 작성한다.
- React Testing Library를 활용해 컴포넌트의 렌더링 결과와 사용자 상호작용을 기준으로 주요 컴포넌트의 동작을 검증한다.
- Playwright를 활용해 실제 브라우저 환경에서 주요 사용자 시나리오가 정상적으로 동작하는지 E2E 테스트를 작성한다.

## 관찰 - 적용 후

> 적용 후 무엇이 달라졌는지 확인합니다.
> 데이터, 로그, 화면, 대시보드, 팀 피드백, 사용자 반응 등 확인한 것을 남깁니다.

솔직히 말해서 아직 기능을 구현하지 않아서 테스트 코드를 작성하지 않았다.

현재 의존성만 추가하여 예시 테스트 케이스만 작성한 상태다.

단위 테스트(Jest)는 독립적으로 검증 가능한 순수 함수, 유틸 함수, 비즈니스 로직에 적용한다.

통합(RTL) 테스트는 여러 컴포넌트를 묶은 상위의 컴포넌트에서 실제 사용자의 조작을 기준으로 동작을 검증한다.

E2E 테스트(Playwright)는 하나의 화면이 아닌 여러 화면과 기능을 거치는 핵심 사용자 시나리오를, 실제 브라우저 환경에서 처음부터 끝까지 검증한다.

의존성이 적고 빠르게 확인 가능한 것은 하위 계층에, 실제 환경에 가까울수록 상위 계층에 배치한다.

우리의 구현 예시를 하나 들어보면

스터디원이 공지를 읽을때 스크롤을 끝까지 내려야 상태(읽음/안읽음)를 전환할 수 있는 버튼이 활성화 된다.

여기서 통합테스트는 단지 스크롤을 끝까지 내렸을때 버튼이 활성화되었는지 확인한다.

하지만 E2E로 작성하면 버튼이 활성화된걸 넘어서 클릭하고 이후의 영향까지 검증할 것이다.

## 기록과 설명

> 수행 내용과 판단 근거를 문서로 남깁니다.

### 테스트 전략

#### Jest 선택 근거

만약 우리의 프로젝트가 Vite기반이었다면 고민하지 않고 Vitest를 선택했을거 같다.

하지만 현재 우리의 프로젝트는 Vite기반이 아니다.

번들러로 Webpack을 사용하고 있다.

그리고 loader로 babel-loader를 사용한다.

Jest를 사용하게 되면 설정파일을 공유할 수 있다.(`babel.config.js`)

추가로 이후에 RN 과 Expo를 도입할 예정이다.

RN의 번들러인 Metro 또한 babel기반인 babel-preset-expo를 사용하기 때문에 `babel.config.js` 를 공유할 수 있다.

즉 웹, 앱, 테스트 세곳다 동일한 설정파일로 관리할 수 있다.

우리가 만약 Vitest를 사용하게 된다면 이후에 앱때문에 Jest가 필요한 상황이 생길 수 있다.

결국은 둘 다 두게되는 불상사가 생길 수 있다. (물론 Vite기반도 대응할 수 있지만 안정성면에서 차이가 존재한다.)

Vitest의 속도를 포기하고 Jest를 선택한다.

우리의 프로젝트에는 Jest를 사용했을때 프로젝트 관리 관점에서 통합시킬 수 있는 지점들이 많다.

추가로 Jest 30은 속도면에서 많이 개선되었다.

우리가 만약에 “속도”라는 측면에서 힘듦을 겪을때 그때 가서 Vitest로 전환하고 Vitest로 전환했을때 생기는 차이점들을 매꿔야할 무게를 감수하면 된다.

#### React Testing Library 선택 근거

Storybook과 RTL 중에 RTL을 선택했다.

Storybook을 사용해 컴포넌트 테스트를 할 순 있지만 RTL을 완전히 대체하기엔 어렵다고 판단된다.

컴포넌트가 이 상태에선 어떻게 보일지를 확인하기 보다는 사용자의 조작에 따라 제대로 작동하는지 확인하는 것이 테스트라고 생각을 한다.

RTL은 실제 사용자가 화면을 사용하는 방식에 가깝게 요소를 조회하고 클릭, 입력 등의 상호작용을 통해 컴포넌트의 동작을 검증하는 데 적합하다.

또한, Jest와 같은 테스트 러너에서 실행할 수 있어 Storybook 개발 서버를 별도로 실행하지 않고도 테스트할 수 있다.

따라서 CI 환경에서 테스트를 자동으로 실행하고 결과를 검증하려는 우리 프로젝트의 목적에는 RTL이 더 적합하다고 판단하였다.

#### Playwright 선택 근거

Cypress와 Playwright 모두 실제 브라우저 환경에서 사용자의 흐름을 검증하는 E2E 테스트 도구이다.

E2E 테스트의 가장 큰 문제점을 생각해보면 속도인거 같다.

아무래도 여러 셋업이 필요하다보니 어떤 도구를 선택하든 테스트가 오래걸린다.

그런 면에서 병렬성을 무료로 지원하는 playwright가 조금 더 낫다고 생각했다.

그리고 Cypress 자체는 정말 많은 기능이 제공되어 DX 적인 면에서 아주 우수한 라이브러리라고 생각한다.

> [!TIP]
> **Cypress도 병렬성을 지원한다.**
>
> CLI만으로는 "각 워커가 어떤 스펙을 실행할지" 로드밸런싱 해주지 않는다.
>
> 그래서 실질적인 병렬화를 하려면 Cypress Cloud를 붙여야 하는데 유료다.

하지만 이러한 기능보다는 속도가 더 우선이라고 판단했다.

그런면에서 병렬 실행(지정 무료)이 기본 내장되어 있는 playwright가 우수하다고 생각했다.

이런 이점은 CI에서도 해당 테스트를 수행해야기 때문에 더더욱 유의미하다.
