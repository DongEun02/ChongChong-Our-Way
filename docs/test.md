## 이유 확인 - 시작 전

테스트 환경이 없으면 기능 추가 이후 정상적으로 동작하는지 자동으로 확인할 수 없고 의도한대로 기능이 동작하는지, 혹시 다른 기능에서 오류가 발생한 건 아닌지 직접 확인해야 한다.

실제로 이전 프로젝트에서 컴포넌트 테스트나 E2E 테스트 코드를 작성하지 않아 기능을 추가하거나 리팩토링 후, 개발 서버를 열어 직접 조작하며 정상 동작하는지 확인해본 경험이 있다.

특히 공통 컴포넌트를 수정할 때 테스트 코드의 필요성은 더 중요해진다. ‘공통’인 만큼 해당 컴포넌트를 사용하는 곳은 다양하다. 하지만 이를 개발자가 모두 직접 확인하는 것은 효율적이지 않고 ‘모든 곳’을 확인해야 하기에 실수를 유발할 수 있다.

테스트는 우리가 지켜야할 최소한의 경계를 의미하며 우리가 코드를 수정했을때 그 경계를 깨트리지 않았는지 확인할 수 있게 해준다.

이로써 리팩토링과 같은 작업에서 안정성적인 측면에 아주 좋은 자신감을 채워준다.

## 적용 - 실제 서비스에

프로젝트의 테스트 범위를 단위 테스트, 컴포넌트 테스트, E2E 테스트로 구분하고 각각 Jest, React Testing Library, Playwright를 적용한다.

테스트 전략은 다음과 같다.

- Jest를 활용해 유틸 함수와 비즈니스 로직 등 독립적으로 검증할 수 있는 코드의 단위 테스트를 작성한다.
- React Testing Library를 활용해 컴포넌트의 렌더링 결과와 사용자 상호작용을 기준으로 주요 컴포넌트의 동작을 검증한다.
- Playwright를 활용해 실제 브라우저 환경에서 주요 사용자 시나리오가 정상적으로 동작하는지 E2E 테스트를 작성한다.

추가로 우리는 적용과 더불어 어떻게 하면 더 좋은 테스트 코드를 잘 작성할 수 있는지에 대한 고민을 했다.

예시로 RTL을 기준으로 하면 모킹을 최소화하여 핸들러의 형태가 변경되었을때도 응답의 구조를 바꾸지 않게 만들거나 DOM 구조에 결합되는 선택자를 지양하는 식으로 테스트와 무관하게 DOM 구조의 변경
으로 깨지는 테스트가 만들어지지 않도록 했다.

또한 E2E의 경우에도 아직은 작성하지 않았지만 전부 다 테스트하는게 아닌 사용자의 핵심적인 흐름을 기반으로한 테스트를 작성할 예정이다.

예시를 들면 "사용자가 스터디를 생성한다", "사용자가 스터디를 참여한다"와 같이 핵심적인 비즈니스 로직을 작성하는 것이다.

"스터디 이름을 입력하지 않았을때 안내 문구가 표시되는가", "특정 필수입력을 하지 않았을때 버튼이 비활성화인지"와 같은 조금 더 세부적인 검증은 최대한 RTL로 작성한다.

결국 E2E는 큰 핵심흐름인 비즈니스 로직을 위주로 하고 그 비즈니스로직을 수행했을때 실제로 데이터가 추가되었는지 까지 확인하여 실제 사용자의 큰 흐름에서 우리의 예상대로 동작하는지 확인하는 테스트를 작성한다.

추가로 브라우저 뒤로가기, 스크롤 이벤트와 같이 브라우저 이벤트로 처리해야하는 부분 또한 E2E로 작성한다.

예시를 들면 "과제 작성하기 퍼널 3페이지에서 브라우저 뒤로가기를 클릭했을때 2페이지로 이동한다"와 같이 브라우저 뒤로가기 같은 동작이 포함되었을때는 RTL로 작성하기 어렵다.

작성이 가능하더라도 과한 모킹동작이 발생하기 때문에 실제 브라우저를 조작하여 뒤로가기를 수행하고 예상대로 동작하는지 확인하는 테스트를 작성한다.

간단하게 브라우저와 연관된 동작을 통한 검증이 필요할때는 E2E 테스트를 통해 작성할 예정이다.

시각적인 부분에서는 Storybook을 통해 확인할 예정이다.

MSW 브라우저 모킹을 통해서 확인이 가능하지만 매번 그 상황으로 직접 이동하기는 번거롭다.

또한 브라우저 내부에서 테스트하기 어려운 UI도 많다.

예시를 들자면 네트워크 연결이 끊겼을때 어떤 UI가 보여질지 확인하려했을때 브라우저 개발자 도구를 조작해야한다.

이 과정에는 도구를 조작하는 비용이 들어 관찰하고 다시 돌려놓기까지 생각보다 큰 비용이 생긴다.

그래서 Storybook을 통해 특정 상황에서 어떤 UI가 보이는지 시각적으로 편하게 확인할 수 있는 환경을 만든다.

또한 자주 발생할것과 같은 문제들은 시각적 회귀 테스트를 통해 스크린샷을 통해 이전 UI와 동일한지 비교한다.

## 관찰 - 적용 후

단위 테스트(Jest)는 독립적으로 검증 가능한 순수 함수, 유틸 함수, 비즈니스 로직에 적용한다.

통합(RTL) 테스트는 여러 컴포넌트를 묶은 상위의 컴포넌트에서 실제 사용자의 조작을 기준으로 동작을 검증한다.

E2E 테스트(Playwright)는 하나의 화면이 아닌 여러 화면과 기능을 거치는 핵심 사용자 시나리오를, 실제 브라우저 환경에서 처음부터 끝까지 검증한다.

의존성이 적고 빠르게 확인 가능한 것은 하위 계층에, 실제 환경에 가까울수록 상위 계층에 배치한다.

우리의 구현 예시를 하나 들어보면

스터디원이 공지를 읽을 때 스크롤을 끝까지 내려야 상태(읽음/안읽음)를 전환할 수 있는 버튼이 활성화된다.

통합(RTL) 테스트에서는 스크롤 끝에 도달했는지에 대한 조건을 제어하여, 도달하기 전에는 버튼이 비활성화되고 도달한 후에는 활성화되는지 검증한다.

E2E 테스트에서는 실제 브라우저에서 공지를 끝까지 스크롤했을 때 버튼이 활성화되는지 확인한다. 이어서 버튼을 클릭해 읽음 상태로 변경하고, 공지를 다시 조회해 변경한 상태가 유지되는지까지 검증한다.

## 기록과 설명

### 테스트 전략

#### Jest 선택 근거

만약 우리의 프로젝트가 Vite기반이었다면 고민하지 않고 Vitest를 선택했을거 같다.

하지만 현재 우리의 프로젝트는 Vite기반이 아니다.

번들러로 Webpack을 사용하고 있다.

그리고 loader로 babel-loader를 사용한다.

Jest를 사용하게 되면 설정파일을 공유할 수 있다.(`babel.config.js`)

추가로 이후에 RN 과 Expo를 도입할 예정이다.

RN의 번들러인 Metro 또한 babel기반인 babel-preset-expo를 사용하기 때문에 `babel.config.js` 를 공유할 수 있다.

즉 웹, 앱, 테스트 세곳다 동일한 설정파일로 관리할 수 있다.

우리가 만약 Vitest를 사용하게 된다면 이후에 앱때문에 Jest가 필요한 상황이 생길 수 있다.

결국은 둘 다 두게되는 불상사가 생길 수 있다. (물론 Vite기반도 대응할 수 있지만 안정성면에서 차이가 존재한다.)

Vitest의 속도를 포기하고 우리는 관리측면에서 Jest를 선택한다.

우리의 프로젝트에는 Jest를 사용했을때 프로젝트 관리 관점에서 통합시킬 수 있는 지점들이 많다.

추가로 Jest 30은 속도면에서 많이 개선되었다.

우리가 만약에 “속도”라는 측면에서 힘듦을 겪을때 그때 가서 Vitest로 전환하고 Vitest로 전환했을때 생기는 차이점들을 매꿔야할 무게를 감수하면 된다.

#### React Testing Library와 Storybook 사용 근거

컴포넌트의 동작과 상태별 UI를 확인하기 위해 RTL과 Storybook을 함께 사용한다.

우리 프로젝트에서는 사용자의 조작에 따른 컴포넌트간의 상호작용, 동작 검증은 RTL로 작성한다.

그리고 특정 상황에서 컴포넌트가 어떻게 보이는지에 대한 시각적 확인은 Storybook으로 수행할 예정이다.

RTL에서는 사용자가 화면을 사용하는 방식에 가깝게 요소를 조회하고 클릭, 입력 등의 상호작용을 통해 컴포넌트의 동작을 검증한다.

예를 들어 필수 입력값이 없을 때 안내 문구가 표시되는지, 입력 조건을 만족하면 버튼이 활성화되는지 확인한다.

이러한 테스트는 기존에 선택한 Jest 환경에서 실행하고, CI에서도 자동으로 실행해 기능 변경에 따른 동작 오류를 확인한다.

Storybook에서는 로딩 중, 데이터가 없는 상태, 네트워크 오류 등 특정 상황을 스토리로 작성해 각 상태의 UI를 시각적으로 확인할 예정이다.

매번 서비스 화면에서 해당 상황을 직접 재현하지 않아도 컴포넌트의 표시 상태와 레이아웃을 반복해서 확인할 수 있도록 한다.

또한 공용 컴포넌트의 문서화를 통해 팀원들 간에 공용컴포넌트 사용방식에 대한 가이드라인을 제공하여 더 쉽게 API를 사용할 수 있는 환경을 만들어 나간다.

이처럼 RTL로 사용자 상호작용에 따른 동작을 검증하고, Storybook으로 상태별 UI를 확인, 문서화하는 역할을 나누어 두 도구를 함께 활용한다.

#### Playwright 선택 근거

Cypress와 Playwright 모두 실제 브라우저 환경에서 사용자의 흐름을 검증하는 E2E 테스트 도구이다.

E2E 테스트의 가장 큰 문제점을 생각해보면 속도인거 같다.

아무래도 여러 셋업이 필요하다보니 어떤 도구를 선택하든 테스트가 오래걸린다.

그런 면에서 병렬성을 무료로 지원하는 playwright가 조금 더 낫다고 생각했다.

그리고 Cypress 자체는 정말 많은 기능이 제공되어 DX 적인 면에서 아주 우수한 라이브러리라고 생각한다.

> [!TIP]
> **Cypress도 병렬성을 지원한다.**
>
> CLI만으로는 "각 워커가 어떤 스펙을 실행할지" 로드밸런싱 해주지 않는다.
>
> 그래서 실질적인 병렬화를 하려면 Cypress Cloud를 붙여야 하는데 유료다.

하지만 이러한 기능보다는 속도가 더 우선이라고 판단했다.

그런면에서 병렬 실행(지정 무료)이 기본 내장되어 있는 playwright가 우수하다고 생각했다.

이런 이점은 CI에서도 해당 테스트를 수행해야기 때문에 더더욱 유의미하다.
