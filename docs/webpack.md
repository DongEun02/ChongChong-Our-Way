# Webpack 기반의 React & TypeScript 개발 환경 세팅

## 이유 확인 - 시작 전

> 이 요구사항이 왜 주어졌는지, 어떤 경험을 만들기 위한 것인지 파악합니다.
> **적용 전 상태(문제, 불편, 위험, 비효율, 학습 공백)를 먼저 남깁니다.**

Vite를 사용했을때 번들링 관련 문제나 셋업 과정에서 어떻게 해야 하는지 하나도 이해하지 못했다.

만약 설정과 관련된 문제가 생겼을때 해결하기 어려워 AI의 도움을 무조건적으로 의존할 수 밖에 없었다.

심지어 특정 설정이 추가될때 “그냥 아 이렇게 해야 되는구나 ~ “라고 생각하고 넘어가 다시 환경설정 해야하는 상황과 마주하면 똑같은 문제를 매번 겪었다.

애초에 번들링 사이즈까지 고려해본적이 없다.

이후에 비정상적인 번들링 사이즈 요청이 온다고 할지라도 의문또한 품지못했다.

이 사이즈가 네트워크별로 유의미하게 영향을 줄 수 있는지도 알지 못했다.

추가적으로, TypeScript를 사용하는 경우, import 파일 확장자를 명시해줘야지만 오류가 발생하지 않고 정상적으로 동작하는 경우가 많았다. 이때 오류가 발생하는 원인을 파악하지 못해 AI를 사용해 해결한 경험이 있다.

## 적용 - 실제 서비스에

> 기술을 학습하고, 실제 팀 프로젝트 서비스에 적용합니다.

webpack 설정을 처음부터 만들어 나갔다.

진입점과, 모드를 설정하고 각 모듈의 규칙을 정했다.

특정 확장자에는 어떤 로더가 사용되는지 지정하고(ts, tsx → babel-loader) `node_modules`와 같은 특수한 폴더들은 제외했다.

여기서 loader는 웹팩에게 통역사와 같은 역할을 한다.

통역사는 왜 필요할까 ?

기본적으로 웹팩은 `.js`, `.json` 확장자만 이해할 수 있다.

그렇기에 `.ts`, `.tsx` 같은 파일을 처리하려면 로더를 통해 웹팩이 이해할 수 있는 JS로 변환해야한다.

## 관찰 - 적용 후

> 적용 후 무엇이 달라졌는지 확인합니다.
> 데이터, 로그, 화면, 대시보드, 팀 피드백, 사용자 반응 등 확인한 것을 남깁니다.

번들러, 번들링에 대해서 처음 알게되었다.

이전에는 `Vite`를 통해 쉬운 초기 환경설정을 했다.

자동으로 `Eslint`, 번들러 설정, 로더, 개발서버가 만들어졌다.

하지만 Webpack을 통해 바닥부터 설정해 나가면서 번들러에 대해서 조금씩 알게된거 같다.

번들러가 `.js` , `.json` 확장자만 알 수 있다는것도 알게 되었고 실제로 번들링할때 코드들을 최적화하여 변수명을 줄이고 공백을 제거하며 한줄로 만들어나가는걸 알 수 있었다.

웹이 동작하기 위해 여러개의 파일이 필요하다.

만약 필요한 파일 하나하나를 전부 다 요청하게 되면 많은 네트워크 비용이 발생할것이다.

심지어 캐시또한 적용하기 어려워질 것이다.

우리는 웹을 동작하기 위해서 최소한의 묶음만 필요하다.

그렇기에 번들러는 의존성에 따라 필요한것들을 파악하고 최적화하여 **“마구마구 필요한걸 집어넣은 보따리”**형태로 만든다.

실제로 번들링되었을때 어떻게 되었는지 비교해가면서 번들링의 동작을 경험해볼 수 있었다.

## 기록과 설명

> 수행 내용과 판단 근거를 문서로 남깁니다.

**구축 목록**

1. webpack / webpack-cli
2. Babel로 React + TypeScript 변환
3. tsc로 타입 검사
4. HtmlWebpackPlugin
5. webpack-dev-server
6. ESLint

Webpack을 추가했다. 그리고 `.ts`, `.tsx` 파일도 Webpack이 이해할 수 있는 JS로 변환하기 위해서 다양한 로더도 추가했다.

Webpack에서 개발을 할때 변경사항을 매번 확인하려면 번들링 과정(`webpack<development>`)이 필요했다.

하지만 개발서버(`webpack-dev-server`)를 추가함으로써 매번 필요한 번들링 과정을 스킵할 수 있었다.

Typescript의 버전을 가장 최근 버전인 `^7` 버전이 아닌 `^6`버전을 선택했다.

현재 webpack 생태계의 여러 로더나 툴체인 자체가 내부적으로 TypeScript 컴파일러 API에 의존하는 경우가 많다.

이 API 표면이 TS 7버전에서 아직 노출되지 않아 webpack 로더들이 TS 7버전과 동작하지 않았다.

아직 TS7 버전이 에코시스템 적으로 안정화 되지 않았다고 판단하여 6버전을 선택했다.

loader는 ts-loader, babel-loader, swc-loader 중에 babel-loader를 선택했다.

ts-loader의 장점은 트랜스파일 + 타입 체크를 동시에 수행한다.

즉 `.js`, `.json`으로 변환하기전에 타입체크를 수행한다.

하지만 이 과정을 babel-loader와 swc-loader는 수행하지 않는다.

대신 이 과정을 빌드전에 `tsc -—noEmit`을 통해 충분히 추가하여 해결할 수 있는 부분이다.

따라서 `babel-loader` 와 `@babel/preset-typescript`를 사용하면 TypeScript 코드를 JavaScript로 변환할 수 있으므로 ts-loader 는 별도로 설치하지 않았다. 대신 타입 검사를 위해 TypeScript 컴파일러를 추가로 설치하였다.

swc-loader는 Rust로 작성된 만큼 속도면에서는 최우수하다.

하지만 babel-loader 대비 아직 성숙도가 낮고, 커스텀 변환이 필요할 때 참고할 자료나 기존 플러그인 자산이 상대적으로 적다.

따라서 우리는 babel-loader를 선택했다.

선택한 이유는 풍부한 생태계와 안정적으로 운영된 소위 말하는 근본이기 때문이다.

이 근본은 트러블슈팅할때 정보적인 측면에서도 차이가 크고 각종 프레임워크 프리셋이 이미 검증되어 있기 때문에 설정에 대한 리스크가 적다.

코드 작성 과정에서 발생할 수 있는 문법 오류와 잠재적인 문제를 사전에 발견하고, 팀원 간 일관된 코드 품질을 유지하기 위해 `ESLint`를 추가했다.
